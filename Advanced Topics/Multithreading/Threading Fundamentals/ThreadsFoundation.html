02 — Race condition
What happens when two threads touch the same data
Shared variable: score = 0 · Both threads want to add 1
THREAD A
reads score → 0
adds 1 locally
writes 1 ✓
THREAD B
reads score → 0 ⚠️
adds 1 locally
writes 1 ← overwrites!
Expected: score = 2
but got →
Actual: score = 1 💥
Why it happens — the three dangerous steps
READ
→
MODIFY
→
WRITE
If thread gets interrupted between READ and WRITE, another thread reads the old value. Silent bug — no crash, wrong answer.

04 — Deadlock
The circular wait — nobody moves
Thread A
holds Lock 1
wants Lock 2
Lock 1 🔒

⇅
Lock 2 🔒
Thread B
holds Lock 2
wants Lock 1
→ A waits for B · B waits for A · frozen forever ←
Step-by-step: how a deadlock forms
A grabs L1
+
B grabs L2
✓ both succeed
A wants L2
+
B wants L1
⚠️ both blocked
circular wait — nobody releases
💀 deadlock
4 conditions for deadlock (all must be true)
1. Mutual Exclusion
resource can only be held by one thread
2. Hold & Wait
thread holds one lock while waiting for another
3. No Preemption
nobody can force a thread to release its lock
4. Circular Wait
A waits for B, B waits for A → closed loop
Break ANY one of these → no deadlock possible
🍜 Memory hook: Dining Philosophers — 5 people, 5 chopsticks, everyone grabs left one simultaneously. Nobody can eat. Everyone starves.
05 — How to fix deadlocks
1
Lock ordering — always grab locks in the same order. A and B both do Lock1→Lock2. Circle breaks.
grab L1
→
grab L2
→
work
→
release both
2
Try-lock + timeout — try to grab, give up after Xms. Release what you hold. Retry later.
try lock
fail?→
release all
→
wait · retry
3
Deadlock detection — OS watches for circular waits, kills one thread (the "victim") to break the loop. Databases do this.
detect cycle
→
kill victim thread
→
others proceed
4
Message passing — threads never share resources. They send messages instead. No shared lock = no deadlock. Go, Rust, Erlang use this.
Thread A
─── msg ──→
Thread B
no locks needed
